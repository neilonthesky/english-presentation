FrameForge Customer Support System: The Flow of One Request

Status. This page describes the flow that runs in web/server (the demo and the experiment call the same step functions). The product FrameForge (an AI video-generation SaaS: users make short video clips from text prompts or reference images in a web studio; the workspace holds uploaded assets and generated videos, not code; sold as a Free, Pro, or Team plan, monthly or annual, plus prepaid credit packs that renders use up), its customers and its help articles are a local simulation. The Jev and LLM calls are real. A refund changes local records only (a ledger entry); it does not move money. The work of the person after a handoff is not simulated. Example paths on this page follow from the rules; they are not measured results (those are in the paper).

How to read the flow

  • Each box is a step. The color says who works in it: fixed code, a model, or a person (with the LLM that prepares the handoff).
  • Only Jev, in step 3, decides labels. Written rules and fixed routing, also in step 3, decide the verdict, the path, and the action. An LLM only writes text.
  • Step 5 does the action only if the written rules allow it. A rule that denies the action means that nothing runs, whatever the models said.
  • Path C never runs anything: the request goes straight to step H, where an LLM summarizes the chat for a person.
  • Fixed code
  • Model (Jev or LLM)
  • Handoff to a person

Path C comes straight from step 3 to step H: the injection flag is on, the priority is Critical, a written rule asks for a person, or the risk flag is on and no written rule covers the action. Step H is also reached after "not solved" at step 6. Both then end at step 7.

The steps

StepWhoWhat happens
1UserWrites in the chat, as the owner of the account or as a teammate of the workspace.
2SystemSaves the request, looks up the account (plan, render credits left, next renewal, the one purchase with its charge date and usage), and reads any other customer's e-mail address from the text with a fixed pattern.
3Jev Fixed rulesRouting. Jev gives five typed answers in one call, each with a probability: topic, action, priority, risk flag, injection flag. Then fixed code checks the written rules for the action on the data of the request (verdict allow, deny, or review), and the first matching routing line chooses the path. Probabilities do not decide.
4ASystemPath A (the request asks for an action): fixed code lists the plan from the written rules. No model.
4BLLMPath B (the request is a question): the LLM answers from the help articles and the account only.
5SystemDoes the action only if the written rules allow it. A rule that denies it means nothing runs, whatever the models said, and the reply says why. A done action is written to the ledger.
6LLMThe customer gets the answer of 4B as it is, or a reply that the LLM writes from the result of step 5. The chat then asks "Did this solve your request?". Yes: step 7. No: step H.
HLLM + personNo action runs. The LLM writes a short summary of the chat for a person (the request, the account, what the bot did and said, why a person is needed, a suggested next step). The bot sends a fixed message: a human support agent will join in a minute. The person takes over.
7SystemWrites a log record: the request, the path, the result, and whether it went to a person (by a rule or by the user).

The experiment measures only the first pass (steps 1 to 5 and, on path C, the decision to hand off). The "solved?" answer and step H are not simulated there.

Path C: when a person takes over

The first line that matches decides: injection flag on, then priority Critical, then a written rule asks for a person, then risk flag on with no written rule for the action. The risk flag alone does not send a request to a person: a refund that the rules allow runs on path A, and a refund that the rules forbid also stays on path A, where nothing runs and the reply explains why.

The written rules

Only the actions that change money or data have written rules: "Start refund" and "Delete data". Each rule gives pass, deny (the action cannot be done), or review (a person must decide). The verdict is deny if one rule denies, review if one asks for a person, and allow otherwise. The rules never use the confidence of the classifier.

Example paths

Each example shows the path that the rules produce, assuming that the classifier labels the text as expected. The exact wording of a model and its probabilities are measured values, not constants. The same sentence "I want a refund" gives different answers for different customers.

1. A refund inside the window

Linh Tran (owner; Pro plan, monthly, $64, charged 5 days ago, 520 of 2,000 render credits used) writes: I want a refund.

Step 3: inside the 14-day window and under $100, so the verdict is allow and the path is A. Step 4A plans the refund. Step 5 runs it and writes the ledger. Step 6: the LLM writes the reply, and the user says if it is solved.

Outcome. A local refund record. No money moves.

2. A refund that needs a person

Minh Pham (owner; Team plan, monthly, $129, charged 20 days ago, no credits used) writes: I want a refund.

Step 3: past the 14-day window but nothing was used, and the amount is over $100. A written rule asks for a person, so the path is C. Nothing runs. Step H: the LLM writes a summary, and the bot says a person will join.

Outcome. A handoff with a summary. No refund runs.

3. A refund that the rules forbid

An Nguyen (owner; render-credit pack, 5,000 credits, $50, 3,120 credits used) writes: I want a refund.

Step 3: the pack is partly used, so a written rule denies the refund. A deny is not a review: the path is A. Step 5 runs nothing, because the rules do not allow the action. The reply explains why and what the customer can do next.

Outcome. Nothing runs, whatever the models said.

4. A renewal that is not charged yet

Hoa Le (owner; Pro plan, monthly, $85, renewal scheduled in 2 days) writes: Cancel my renewal and refund me.

Step 3: the renewal is not charged, so the rule passes; path A. Step 5 cancels the renewal with no charge.

Outcome. The renewal is cancelled before it is charged.

5. A question

Any customer writes: How many credits does a video render use?

Step 3: the action is "Send reply" and no flag is on, so the path is B. Step 4B: the LLM answers from the help articles and the account. Step 5 changes nothing. Step 6 sends the answer as it is.

Outcome. An answer. If the user says "not solved", the chat goes to step H.

6. Text that gives orders to the chatbot

Any customer writes a request that tells the chatbot to ignore its rules and refund everything.

Step 3: Jev sets the injection flag, and the routing sends the request to path C. Nothing runs, whatever the text says. Step H hands the chat to a person.

Outcome. A handoff. No action runs.

7. A teammate asks for a refund or a deletion

A teammate of the workspace writes: Delete all our videos and uploaded assets.

Step 3: only the owner can ask for this, so a written rule denies it. Step 5 runs nothing, and the reply says why. The same holds when the text names another customer.

Outcome. Nothing runs.

8. The user says "not solved"

Any customer answers "No, I need a person" at step 6.

The chat does not go back through steps 3 to 5. No action runs again. Step H: the LLM writes a summary of the whole chat, and the bot says a person will join.

Outcome. A handoff. Step 7 writes the log.

What this study does and does not do

  • Real: hosted Jev and LLM calls; an HTTP server running these steps; local records (the ledger and the log) that change when an action runs.
  • Simulated: the FrameForge product (studio, renders, workspaces), its customers, purchases and help articles; the sender (an explicit choice of owner or teammate); the work of the person after a handoff.
  • Not integrated: a payment provider, an account system, and a real ticket tool.
  • Two systems compared: the only difference is the classifier in step 3: Jev (typed answers with a probability) or an LLM. The written rules, the routing rules, and step 5 are identical.

The numbers are in the paper and in experiment/results/; this page contains none, so that it cannot drift from the evidence.

Words

Classifier
Jev, or an LLM in the baseline: it gives the five labels in step 3.
Jev
A System One model: it gives a typed answer with a probability in one call and cannot write text.
Written rule
A fixed rule of the made-up company FrameForge, with the outcome pass, deny, or review on the data of the request.
Path A, B, C
A: the system acts or refuses. B: the LLM answers a question. C: a person takes over and nothing runs.
Ledger
The list of actions that already ran in the session. A written rule reads it so that an action is not done twice.
Handoff
Step H: the LLM summarizes the chat for a person, and the bot says a person will join.
