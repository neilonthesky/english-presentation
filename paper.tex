\begin{abstract}
Customer support for a software-as-a-service (SaaS) product can run in three ways. We build them as three levels of one ladder and measure them on the same 50 requests in 24 types for FrameForge, an AI video-generation service. Level 1: support staff read every request (an assumed 90~s each). Level 2: one large language model (LLM) agent reads the chat and the account, applies the written rules itself, and either runs an action or denies it. Level 3: Jev, a fast classifier, answers five fixed questions about the request; fixed code reads only the account fields that the action needs and checks the written rules; the LLM writes the text. Level 2 serves 32 requests, stops 15 (a written rule denies the action), and makes 3 errors; Level 3 serves 35, stops 15, and makes 0. Neither level runs a harmful action. With 3 discordant pairs (requests where only Level 2 errs) the sign test gives \(p = 0.25\), so an accuracy gap is not established at 50 requests. Level 3 is never worse in any measure, 2.2 times faster (3.16~s against 6.85~s), and 2.4 times cheaper (\$0.302 against \$0.712 per 1,000 requests). As a classifier, Jev is 18 times faster and 11 times cheaper than the LLM, but it is less accurate on four of the five answers.
\end{abstract}

\section{Introduction}

Large language models (LLMs) now read customer requests and act on them, and text in a request can carry prompt-injection orders for the model~\cite{greshake2023injection}. When the system can start a refund or delete customer data, one wrong action does real harm, and support staff who read every request are slow and costly.

We study one \emph{ladder} of three levels, from the traditional workflow of support staff to a modern AI-agent system. Each level changes one part of the level before it, and all levels run on the same requests. The case is FrameForge, an AI video-generation SaaS sold as subscription plans and credit packs. Jev~\cite{almeida2026jev} is a fast classifier that gives typed labels, each with a confidence, and cannot write text. We ask two questions:
\begin{itemize}
    \item \textbf{Question 1.} What does each level buy and cost: requests served, requests stopped by a written rule, errors, harmful actions, time, and API cost?
    \item \textbf{Question 2.} What changes when Jev replaces the LLM as the classifier?
\end{itemize}

\section{Related Work}\label{sec:related}

\textbf{Prompt injection.} Text in data can carry orders for a model~\cite{greshake2023injection}; CaMeL~\cite{debenedetti2025camel} and the design patterns of Beurer-Kellner et al.~\cite{beurer2025patterns} defend by limiting what the model can trigger. Support platforms route tickets by rules~\cite{zendesk2026routing}; we build a small system of this kind, with fixed code that checks every action.

\textbf{Support agents.} The Fin agent runs refunds, cancellations, and password resets, and reports 76 percent resolution without a human~\cite{intercom2026fin}. Intent sets are broad: Bitext holds 27 intents~\cite{bitext2023intents}, guides advise fewer than 20 ticket categories~\cite{tettra2024categories}, and a router label is worth keeping only if one routing action follows~\cite{buildspacelabs2026intents}. We cover five actions.

\section{Design of the System}\label{sec:design}

\subsection{The Three Levels}\label{sec:steps}

The ladder changes one part at a time. Level 1 to 2 replaces the staff with one LLM that does the whole job. Level 2 to 3 splits that job between a fast classifier, fixed code, and an LLM writer.

\textbf{Level 1 (Staff only).} Support staff read every request, decide it, and act (Figure~\ref{fig:staff}). No model runs. We assume 90~s of work per request, and this level is the baseline.

\textbf{Level 2 (LLM agent).} One agent call reads the request text, the sender role, the help articles, and the full account. The agent applies the written rules (Section~\ref{sec:rules}) itself and returns one of two answers: an action to run with its target, or a denial that names the rule. The action that it names runs at once: no fixed code checks it, and nothing handles an order hidden in the text (Figure~\ref{fig:llmagent}). The LLM then writes the Final message.

\textbf{Level 3 (Jev + LLM + rules).} Jev replaces the agent as the step that reads the chat. In one call it answers five questions, each with a confidence, and it never reads the account: the \emph{topic} (the subject of the request: Account, Payments, Plans and Credits, Product Help, Refunds, or Security), the \emph{priority}, the \emph{action} (Send reply, Start refund, Delete data, Cancel plan, or Reset password), a \emph{risk flag} (money, stored data, the plan, or the password is at stake), and an \emph{injection flag} (the text gives orders to the model). Fixed code does the other jobs of the agent: Gather info reads only the account fields that the action needs, and Rules check applies the written rules. The LLM writes the text only (Figure~\ref{fig:flow}).

\subsection{The Flow of One Request at Level 3}\label{sec:flow}

Figure~\ref{fig:flow} shows Level 3 as a state machine with eight states.

\textbf{Triage.} Jev answers the five questions in one call. Fixed code then applies one routing rule: if the injection flag is on, the action is set to ``Send reply'', so the orders in the text are ignored. If the classifier answer is invalid, nothing runs.

\textbf{Gather info and Rules check.} Gather info is fixed code. It reads the help articles, any e-mail address in the text, and only the account fields that the action needs (Table~\ref{tab:fields}), taken from the fields that each written rule reads. Rules check applies the written rules of the action to those fields: allow goes to Do action, and deny goes to the Final message with nothing run. A rule that needs a field outside the selection denies; this never happened on the 50 requests.

\subsection{The Written Rules}\label{sec:rules}

Four actions that change the state have written rules (Table~\ref{tab:rules}); ``Send reply'' has none. Each rule gives allow or deny only: deny means nothing runs and the Final message explains. One deny is enough, and deleting data is always denied because it cannot be undone. The \emph{Security rule} is checked first and covers every state change: a request that reports that the account or the payment method was used by someone who is not the customer stops it, and the reply gives the security steps. At Level 3 the rule applies when the topic of the request from Triage is ``Security''; at Level 2 the agent reads the text of the rule.

A seeded generator (seed 20261007) writes 50 requests in 24 types (Table~\ref{tab:types}); there is one request set and no split. Every request has its own wording, its own sender (44 owners and 6 teammates), and a customer from the test data. The correct labels come from the written rules: the generator runs the real code of the system on the correct action, the true sender, the facts in the text (for example, an e-mail address), and the refund history of the customer. A written rule denies the action on 15 of the 50 requests, and the flow then runs nothing; 26 end with an answer, and 9 run an action. One closing message has no right topic, so its topic label is not scored.

\subsection{Models and Run}\label{sec:api}

The classifier of Level 3 is Jev (version \nolinkurl{jev-1.13.0}), a fast classifier from the \emph{System One} family. The LLM is \nolinkurl{deepseek-v4.1-flash} through the DeepSeek API, with high reasoning effort, temperature 0.3, and a 4000-token limit. The agent of Level 2 makes two calls per request: the agent call (run or deny, in strict JSON) and the Final message. At Level 3 the LLM writes the Final message only. The \emph{LLM-classifier run} of Section~\ref{sec:results} uses the same LLM as a five-field classifier in the flow of Level 3; it is not a level of the ladder, and it feeds Question 2.

Both classifiers get the same input: the chat text, the sender role, the channel ``chat'', and the matching help articles; the account is not read at Triage. The label definitions are neutral: one rule for each question, no request type, and no example phrase; the risk flag covers money, stored data, the plan, and the password. The agent of Level 2 reads the same action criteria, the text of the written rules, and the full account. The LLM gives no confidence, and an invalid answer runs nothing; none occurred in the reported run.

A full run makes 300 model calls: 100 each at Level 2, at Level 3, and in the LLM-classifier run. The final recording made 105 live LLM calls and no live Jev call, about \$0.03 at list price, and an offline replay of the main run reproduces every number in this paper. Code, data, and recordings are in \texttt{experiment/}.

We use list prices: Jev costs \$0.042 per million input tokens, and its output tokens are free; the LLM costs \$0.15 per million input tokens and \$0.60 per million output tokens (off-peak price, no cache discount), and the recorded output tokens include the reasoning tokens.\footnote{\url{https://docs.typesafe.ai/models}; \url{https://api-docs.deepseek.com/quick_start/pricing/}}

\subsection{Metrics}\label{sec:metrics}

A request ends in one of three \emph{outcomes}, seen from the customer. \emph{Served}: the run ends with the correct final result, an answer or an action that the written rules allow. \emph{Stopped}: a written rule denies the correct action, nothing ran, and the reply gave the reason. \emph{Error}: every other run. A run is \emph{harmful} if it changes state (money, data, the plan, or the password) against the written rules. \emph{Label errors} count the runs whose action label differs from the correct action, whatever the customer saw. \emph{Total time} is the sum of the API response times of one request at Levels 2 and 3, and the assumed 90~s at Level 1. \emph{API cost} is in US dollars per 1,000 requests, and \emph{latency} is the median and the 95th percentile of one classifier call. A confidence is calibrated if answers at 0.90 are right about 90\% of the time; the expected calibration error (ECE) compares confidence and accuracy in ten equal bins. Two levels are compared with an exact two-sided sign test over the same 50 requests, one pair for each request; only discordant pairs, where one level errs and the other does not, count. With zero harmful actions in \(n\) requests, the 95\% upper limit of the harmful rate is about \(3/n\) (the rule of three).

Table~\ref{tab:ladder} answers Question 1. Level 1, the baseline, makes no error and uses 90~s of assumed staff time per request.

Level 2 serves 32 of the 50 requests, stops 15, and makes 3 errors (6.0\%); Level 3 serves 35, stops 15, and makes 0. Both levels stop all 15 requests that a written rule denies: nothing runs, and the reply gives the rule. The 3 errors of Level 2 are wrong denials: the correct result is an answer; nothing ran in any of them. The sign test has 3 discordant pairs, all errors at Level 2 only, and gives \(p = 0.25\): the accuracy gap is not established. A wrong label is not always a wrong outcome. The label errors are 7 at Level 3 and 5 at Level 2. At Level 3 the Security rule stops the 2 fraud reports among them, and in the other 5 Jev answers ``Send reply'' and nothing runs.

No run is harmful at either level. Level 2 has no fixed check: only the judgment of the agent separates a wrong answer from a wrong action.

Level 3 is 2.2 times faster and 2.4 times cheaper than Level 2. The first call explains most of the gap: the agent call at Level 2 takes 3.11~s per request and costs \$0.386 per 1,000 requests, and the Jev call at Level 3 takes 0.295~s and costs \$0.052. The fields of Table~\ref{tab:fields} cut the Final message input at Level 3 from 617.2 to 589.6 tokens per request (\(-4.5\%\)); we claim this input saving only, because the Final message calls vary between recordings.

The routing rule, the written rules, and the Security rule catch the wrong answers. \section{Discussion and Limits}\label{sec:discussion}

Level 3 buys time and cost, not a proven gain in accuracy: the gap is not established, but Level 3 is never worse in any measure, and the gain comes from the first call, where a fast classifier replaces a reasoning LLM agent. The written rules make a weaker classifier safe: Jev is behind the LLM on four fields, yet no wrong answer becomes an error of Level 3.

\textbf{Limits.} The evidence comes from two hosted models, one synthetic SaaS product, and our own labels: 50 requests in 24 types. Zero money or data harm in 50 requests is not proof of zero (the 95\% upper limit is about 6\%). The popup delay and the silence time \(T\) are not simulated, and the 90~s at Level 1 is assumed. The classifier comparison uses one prompt wording and one run per request, and errors are graded by the action label, not by the reply wording. The Security rule was added after fraud reports showed a defect on these 50 requests, so the main numbers are not a blind test. Time and cost of the Final message calls vary between recordings, Level 2 was recorded at another time than Level 3, and the provider's prompt cache supplied 22.3\% of the input tokens, so the cost of every level is an upper bound.

\section{Conclusion}

We built three levels of customer support on one ladder and measured them on the same 50 requests, by what the customer gets. One LLM agent already serves most requests, but no fixed code stands behind it. Splitting the job at Level 3 (Jev, fixed code, and an LLM writer) gives no error, 2.2 times the speed, and 2.4 times lower cost, and the sign test does not establish an accuracy gap. A Security rule closes the fraud defect that we found on the main set. Future work should test adversarial inputs, real tickets, more request types, and the popup and the silence timer with real customers.
