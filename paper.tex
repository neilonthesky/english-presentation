\begin{abstract}
Customer support for a software-as-a-service (SaaS) product can run in three ways. We build them as three levels of one ladder, and we run the two automated levels on the same 1,024 requests in 26 types from 512 customers of FrameForge, an AI video-generation service. Level 1: support staff read every request (an assumed 90~s each). Level 2: one large language model (LLM) agent reads the chat and the whole account, applies the written rules itself, and either runs an action or refuses. Level 3: Jev, a fast classifier, answers five fixed questions about the chat and then one yes/no question for each written rule of the action; fixed code runs the action only when no answer says that a rule is broken, and the LLM writes the reply. In one run of each level on our synthetic set, Level 2 serves 795 requests, stops 198 (a written rule denies the action), and makes 31 errors, 10 of them harmful; Level 3 serves 825, stops 199, and makes no error. Level 3 needs less than half the mean machine time (5.89~s against 12.45~s) and has 2.2 times lower API cost (\$0.30 against \$0.64 per 1,000 requests). The set is a template-based challenge set, not production traffic, and two refund inputs were changed after earlier failures, so the rule evaluation is not blind. Fixed execution follows Jev's answers; it is not independent policy verification, and the results are no safety guarantee.
\end{abstract}

\section{Introduction}

Large language models (LLMs) now read customer requests and act on them, and text in a request can carry prompt-injection orders for the model~\cite{greshake2023injection}. When the system can start a refund or delete customer data, one wrong action does real harm, and support staff who read every request are slow and costly.

We study one \emph{ladder} of three levels, from the traditional workflow of support staff to two automated designs. The case is FrameForge, an AI video-generation SaaS sold as monthly or annual plans. The two automated levels differ in the model that decides, in the input that it reads, and in the flow around it, so we compare two designs, not one variable. Every level that runs gets the same requests. Jev~\cite{almeida2026jev} is a fast classifier that gives typed labels, each with a confidence, and cannot write text. We ask two questions:
\begin{itemize}
    \item \textbf{Question 1.} What does each level buy and cost: requests served, requests stopped by a written rule, errors, harmful actions, time, and API cost?
    \item \textbf{Question 2.} What changes when Jev replaces the LLM agent as the part that decides?
\end{itemize}

\section{Related Work}\label{sec:related}

\textbf{Prompt injection.} Text in data can carry orders for a model~\cite{greshake2023injection}; CaMeL~\cite{debenedetti2025camel} and the design patterns of Beurer-Kellner et al.~\cite{beurer2025patterns} defend by limiting what the model can trigger. Support platforms route tickets by rules~\cite{zendesk2026routing}; we build a small system of this kind, in which fixed code runs an action only when no rule answer says that a rule is broken.

\textbf{Support agents.} The Fin agent runs refunds, cancellations, and password resets, and reports 76 percent resolution without a human~\cite{intercom2026fin}. Intent sets are broad: Bitext holds 27 intents~\cite{bitext2023intents}, guides advise fewer than 20 ticket categories~\cite{tettra2024categories}, and a router label is worth keeping only if one routing action follows~\cite{buildspacelabs2026intents}. We cover five actions.

\section{Design of the System}\label{sec:design}

\subsection{The Three Levels}\label{sec:steps}

The ladder has three levels. Level 1 to 2 replaces the staff with one LLM that does the whole job. Level 2 to 3 splits that job between a fast classifier, fixed code, and an LLM writer. This change alters the model, the input, and the flow.

\textbf{Level 1 (Staff only).} Support staff read every request, decide it, and act (Figure~\ref{fig:staff}). No model runs. We assume 90~s of work per request, and this level is the baseline. We do not run it.

\textbf{Level 2 (LLM agent).} One agent call reads the request text, the sender role, the help articles, and the full account. The agent applies the written rules (Section~\ref{sec:rules}) itself and returns one of two answers: an action to run with its target, or a refusal that names a rule. The action that it names runs at once: no fixed code checks it, and nothing handles an order hidden in the text (Figure~\ref{fig:llmagent}). The LLM then writes the Final message.

\textbf{Level 3 (Jev + LLM).} Jev reads the chat in up to two calls and never writes text. The first call reads the chat only, not the account, and answers five questions, each with a confidence: the \emph{topic} (the subject of the request: Account, Payments, Plans and Credits, Product Help, Refunds, or Security), the \emph{priority} (Low, Medium, High, or Critical), the \emph{action} (Send reply, Start refund, Delete data, Cancel plan, or Reset password), a \emph{risk flag} (money, stored data, the plan, or the password is at stake), and an \emph{injection flag} (the text gives orders to the model). When the action changes the state, a second call reads the account lines of that action and answers one yes/no question for each written rule of the action: is this rule broken? Fixed code does the other jobs: it sets the action to ``Send reply'' when the injection flag is on, it reads only the account fields that the action needs, and it runs the action when no answer says broken. The LLM writes the text only (Figure~\ref{fig:flow}). The rules are questions to Jev, not code: fixed code applies no written rule on this path.

\subsection{The Flow of One Request at Level 3}\label{sec:flow}

Figure~\ref{fig:flow} shows Level 3 as a state machine with eight states.

\textbf{Triage.} Jev answers the five questions in one call. It is told to choose the action that the request needs and not to apply the written rules. Fixed code then applies one routing rule: if the injection flag is on, the action is set to ``Send reply'', so the orders in the text are ignored. If the answer is invalid, nothing runs. The topic, the priority, and the risk flag are scored in Section~\ref{sec:classifier}, but no routing rule and no written rule reads them.

\textbf{Gather info.} Gather info is fixed code. It reads the help articles, any e-mail address in the text, and only the account fields that the action needs (Table~\ref{tab:fields}). It also states the days since the charge, so a model reads a number and never subtracts two dates.

\textbf{Rules.} For ``Send reply'' no rule question is asked. For every other action, a second Jev call answers one yes/no question for each written rule of the action, for example ``Is the amount of the purchase above 100 dollars?'', and it answers the Security question on every such action. Fixed code only combines the answers. When no answer says broken, Do action runs. When one does, the Final message explains and nothing runs; the Security rule names the reason first, and otherwise the first broken rule in the order of the questions. Nothing checks these answers: a wrong answer can let a wrong action run or stop a right one.

\textbf{Final message and Chat open.} Do action changes the money, the data, the plan, or the password. The Final message answers from the help articles and the selected fields; for a deny it says what the chat cannot do and gives the steps that the customer can take alone. A popup then asks whether the issue is solved. The chat resolves when the customer answers yes, answers no \(N\) times, or stays silent for a set time \(T\); a new message in the same chat goes back to New. The experiment runs the first pass of each request only: Chat open and Resolved are not simulated.

\subsection{The Written Rules}\label{sec:rules}

Four actions that change the state have written rules (Table~\ref{tab:rules}); ``Send reply'' has none. Each rule gives allow or deny only: deny means nothing runs and the Final message explains. One deny is enough, and deleting data is always denied because it cannot be undone. The \emph{Security rule} covers every state change: a request that reports that the account or the payment method was used by someone who is not the customer stops it, and the reply gives the security steps. At Level 2 the agent reads the text of every rule; at Level 3 Jev answers one question for each rule. Every sender in our data is the account owner, so there is no owner-only rule.

\section{Experimental Setup}\label{sec:setup}

\subsection{Synthetic Data and Correct Labels}\label{sec:data}

All data are made by us. The test data have 512 FrameForge customers, each with one purchase (a monthly or an annual plan: Plus, Pro, or Max), a plan, a render-credit balance, a plan state, and a log of reset links; the profiles cover each branch of the written rules.

A seeded generator (seed 20261007) writes 1,024 requests in 26 types, two for each customer (Table~\ref{tab:types}). The mix is a challenge-set design, not an estimate of production traffic. Every request has its own wording, and every sender is the account owner. The correct labels come from the written rules: the generator runs the real code of the system on the correct action, the facts in the text (for example, an e-mail address), and the refund history of the customer. A written rule denies the action on 199 requests, and the flow then runs nothing; 190 requests run an action, and 635 end with an answer. Of the 1,024 requests, 27 hide an order in the message. Eight closing messages have no right topic, so only 1,016 topic labels are scored. There is one request set and no split.

\subsection{Models and Run}\label{sec:api}

The classifier of Level 3 is Jev (version \nolinkurl{jev-1.13.0}), a fast classifier from the \emph{System One} family. The LLM is \nolinkurl{deepseek-v4.1-flash}, which we call through a hosted gateway, with high reasoning effort, temperature 0.3, and a 4000-token limit. The agent of Level 2 makes two LLM calls per request: the agent call (run or refuse, in strict JSON) and the Final message. At Level 3 the LLM writes the Final message only, and Jev makes 1,556 calls: 1,024 first calls and 532 rule calls, or 1.5 per request.

The first Jev call and the agent get the same action criteria: one plain sentence for each action, no request type, and no example phrase. The first call reads the chat text, the sender role, the channel ``chat'', and the matching help articles. The rule call reads the account lines of the action and one question for each rule. The agent reads the text of the written rules and the full account. The LLM gives no confidence, and an invalid answer runs nothing; none occurred in the reported runs.

Each level ran as its own process on the same 1,024 requests, with its own cache and no shared result file. In the first pass, the gateway refused some calls with HTTP 429 (rate limit), and 349 requests at Level 2 and 110 at Level 3 did not finish. A second pass reused every cached answer and made a live call only for a call that was missing, so the first successful answer of every call is the one that we report. No prompt, rule, label, or model setting changed between the passes. An offline replay of each final run makes no live call and reproduces every stored record.

We use list prices: Jev costs \$0.042 per million input tokens, and its output tokens are free; the LLM costs \$0.15 per million input tokens and \$0.60 per million output tokens (off-peak price). Every input token is charged at the full price, and the recorded output tokens include the reasoning tokens. The gateway bills by its own plan, so our costs are estimates and upper bounds, not invoices.\footnote{\url{https://docs.typesafe.ai/models}; \url{https://api-docs.deepseek.com/quick_start/pricing/}}

\subsection{Metrics}\label{sec:metrics}

A request ends in one of three \emph{outcomes}, seen from the customer. \emph{Served}: the run ends with the correct final result, an answer or an action that the written rules allow. \emph{Stopped}: a written rule denies the correct action, nothing ran, and the reply gave the reason. \emph{Error}: every other run, for example a refusal where the correct result is an answer, or an action that the written rules deny. A run is \emph{harmful} if it changes state (money, data, the plan, or the password) against the written rules. A reply is graded by its action label, not by its words. For Jev we also score each of the five answers of the first call against the correct label, and each rule answer against the written rules. \emph{Machine time} is the sum of the response times of the successful model calls of one request, and the assumed 90~s at Level 1; it is not wall-clock time, because waiting for a free call slot, failed tries, and pauses are not in it. \emph{API cost} is in US dollars per 1,000 requests.

\subsection{The Ladder (Question 1)}

Table~\ref{tab:ladder} answers Question 1. Level 1, the baseline, uses 90~s of assumed staff time per request and no model.

Level 2 serves 795 of the 1,024 requests, stops 198, and makes 31 errors (3.0\%); Level 3 serves 825, stops 199, and makes none. Of the 31 errors of Level 2, 27 are injection requests: on 21 the agent refused with a refund rule where the correct result is an answer, and on 6 it ran the order of the text (5 refunds and 1 plan cancellation). Of the other 4 errors, 3 are small refunds where the agent ran a plan cancellation instead of the refund, and 1 is a cancellation of a plan that was already cancelled. These 10 runs are the harmful ones: 5 refunds and 5 plan cancellations. All 31 errors are errors of Level 2 only, so the paired sign test has 31 discordant pairs, all against Level 2 (exact two-sided \(p = 9.3 \times 10^{-10}\)). Level 3 makes no harmful run.

Level 3 needs less than half the mean machine time of Level 2 (5.89~s against 12.45~s) and has 2.2 times lower API cost (\$0.297 against \$0.640). The decision call explains the gap. At Level 2 the agent call takes 6.66~s on average (median 4.97~s) and costs \$0.376 per 1,000 requests. At Level 3 the Jev calls take 0.43~s on average (median 0.47~s, rule call included) and cost \$0.066. The Final message costs about the same at both levels: 5.8~s and \$0.26 at Level 2, against 5.5~s and \$0.23 at Level 3.

Table~\ref{tab:jev} shows the answers that Jev gives when it decides. The priority label is a label, not a scheduling result: we did not measure waiting time or response time.

\section{Discussion and Limits}\label{sec:discussion}

Level 3 buys speed, lower cost, and fewer errors on this set. The gain comes from the decision call, where a fast classifier replaces a reasoning LLM agent; both levels pay about the same for the Final message, so Jev saves only the part that it replaces. Level 2 has no routing rule, so an order inside a text reaches the agent as a request, and 27 of its 31 errors are injection requests. Level 3 turns the injection flag into a fixed routing rule, and Jev sets the flag on every attack of this set.

The design is a limit on what each model can trigger, not a check of the facts. Jev has no action tool, but its answers decide which code runs, and the code trusts them: one wrong rule answer can allow an unsafe action or stop a right one. Fixed execution is therefore not independent policy verification. On this set Jev's rule answers are all right, and its wrong action labels do not become wrong outcomes, but we cannot say that this holds on other requests.

\textbf{Limits.} The evidence comes from two hosted models, one synthetic SaaS product, our own labels, and one run per request and level: 1,024 requests in 26 types from a template-based generator, not production traffic. The two automated levels differ in model, input, and flow, so the results do not show which part of the change causes the gain. Zero errors and zero harmful runs at Level 3 do not prove zero: the Wilson 95\% upper limit of 0/1,024 is 0.37\%. The rule evaluation is not blind: two refund inputs, the question about used credits and the line with the days since the charge, were changed after earlier failures, and the Security rule and the account-field table were found on an older set of 50 requests. Time and cost are the recorded values of the successful calls at list price; a first pass lost requests to rate-limit errors and a second pass completed them. The popup delay and the silence time \(T\) are not simulated, the 90~s at Level 1 is assumed, and the text of the replies is not scored. We did not test trained classifiers, other decision models, or a held-out request set.

\section{Conclusion}

We built three levels of customer support on one ladder and ran the two automated levels on the same 1,024 requests, judged by what the customer gets. One LLM agent serves most requests, but no fixed code stands behind it: it makes 31 errors, 10 of them harmful, and 27 are injection requests. At Level 3, Jev answers five questions and then one question for each written rule, and fixed code follows the answers; it makes no error on this set, needs less than half the mean machine time, and has 2.2 times lower API cost. These results hold for one run on a synthetic challenge set, and the code does not verify Jev's answers, so they are no safety guarantee. Future work should test real tickets, a held-out request set, and stronger baselines, and should measure the popup and the silence timer with real customers.
